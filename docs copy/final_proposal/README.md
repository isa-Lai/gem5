## 1. Executive Summary of the Refined COMPASS v2 Proposal

COMPASS v2 extends the compiler-guided, cross-layer stream architecture of **InterStellar** (MemSys'25) and **COMPASS** (IEEE TC) to test a focused, high-impact architectural hypothesis:

> **Central Hypothesis:** COMPASS can exploit software-exposed stream structure to prepare useful data at the intelligent memory controller (`iMC`) without allocating a Last-Level Cache (LLC) MSHR for every prepared line. A separately controlled delivery stage can then move ready data toward the LLC (`iPF Buffer`) using bounded receiver resources and compact, credit-controlled interval authorisations—increasing useful throughput or reducing exposed demand waiting under constrained concurrency and long interconnect paths at a defensible, fully disclosed hardware cost.

Unlike conventional cache prefetchers (or pushed-prefetch schemes that still allocate per-line cache-side MSHRs), COMPASS v2 separates and coordinates two distinct stages across the cache-memory interface:
1. **Stage 1 — Bounded Independent Preparation at `iMC` ($K$ Future Segments):** Advances DRAM-efficient preparation across up to $K \in \{1, 2, 4\}$ mapped row/page segments per stream without requiring an individual new LLC request arrival to trigger every segment, while obeying per-bank queue caps (`actq`/`pendingActq`), `iBuffer` capacity, and `srTLB` page-mapping boundaries.
2. **Stage 2 — Credit-Controlled Interval Delivery to `iPF` ($W_{\text{del}}$ Distinct Lines):** Replaces per-line initiating pull requests and speculative per-line LLC MSHRs with a persistent, page-bounded **Interval Descriptor**, per-position state bitmaps (`Authorised`, `Completed`, `Resident`, `DemandWait`), exact receiver data-slot conservation ($S_{\text{free}} + S_{\text{reserved\_unfilled}} + S_{\text{resident}} = S_{\text{total}}$), and explicit transport credits.

The proposal is structured around a rigorous **$2\times 2$ factorial comparison** (**A**: Current prep + Line pulls, **B**: Current prep + Interval delivery, **C**: Extended $K$-segment prep + Line pulls, **D**: Combined design), evaluated across a **6-order architecture-first execution sequence** and a **10-stage benchmark roadmap** (starting with private read-only mapped streams on `ddot`, validating write/invalidation/demand-merge paths before `daxpy`/`dscal`, and testing multi-core mixes, 16/32-core scaling, held-out stencils, and bystander pointer-chase/column-walk interference).
